# Released changelog date corrections — the ONE lift on the append-only guard.
#
# `scripts/ci/release_contract.py` proves that `CHANGELOG.md` is append-only
# from the protected base to the head of every range it validates: no released
# version may be removed, reordered, duplicated, or have one byte of its
# entries rewritten. None of that is liftable, and no line in this file can
# make it so.
#
# The single edit a line here authorizes is one released heading's DATE moving
# from one stated value to another stated value, because a heading can be
# wrong about the day a release actually shipped and the record that settles
# it lives outside this file. Naming the exact old date, the exact new date,
# and the record the new date comes from puts that correction where a reviewer
# reads it instead of inside a diff nobody diffed.
#
# An entry is spent as soon as it lands: it names the old date, so once the
# protected base carries the corrected heading there is nothing left for it to
# authorize. A spent entry is therefore inert rather than a red build — it is
# addressed to bytes that no longer exist anywhere in the ladder — and it is
# removed as ordinary housekeeping, never under pressure.
#
# Format, exactly four `|`-separated non-empty fields:
#
#     <version> | <old date> | <new date> | <reason>
#
0.1.7 | 2026-08-11 | 2026-08-10 | Issue #12. Every independent record of v0.1.7 falls on 2026-08-10 in UTC and in the repository's local zone alike: the release merge commit (2026-08-10T21:21:14Z), the annotated tag v0.1.7 (created 2026-08-10T21:24:23Z), and the GitHub Release (published 2026-08-10T21:34:55Z). The heading said 2026-08-11, which no record supports under either reading.
